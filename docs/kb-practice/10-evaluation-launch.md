# 评测与上线：怎么证明它"答得准"

> 约 11 分钟 · 关键词：评测集、忠实度、LLM-as-judge、灰度上线

## 评测集是开发工具，不是验收文档

第 01 篇里提过一句：很多人把评测放到最后，结果前面几个月都在"感觉变好了"。这里把话说透——

**评测集的第一用途是开发，第二用途才是验收。** 它的价值体现在三个时刻：

  <table>
    <tr><th>时刻</th><th>没有评测集会怎样</th></tr>
    <tr><td>选型时（第 05 篇）</td><td>只能看榜单，选出来的模型和你的数据不匹配</td></tr>
    <tr><td>调优时（第 07 篇）</td><td>改了参数不知道变好还是变坏，容易改坏</td></tr>
    <tr><td>上线时（本篇）</td><td>无法回答"能不能给全员用"，只能拍脑袋</td></tr>
  </table>

所以它应该在**第 05 篇之前**就建起来，而不是等到要上线才补。

## 三层指标，从便宜到贵

评测不能只看一个"准确率"。同一批问题要分三层看，因为三层的排查成本和含义完全不同：

  <table>
    <tr><th>层次</th><th>指标</th><th>怎么测</th><th>特点</th></tr>
    <tr><td><strong>检索层</strong></td><td>Recall@K（正确答案在不在前 K）、MRR（排在第几）、命中率</td><td>完全自动，拿标注好的"期望 chunk"对比</td><td>快、稳定、可解释——<strong>应该最先看</strong></td></tr>
    <tr><td><strong>生成层</strong></td><td>忠实度（答案是否只基于给出的片段）、引用准确性、完整性</td><td>人工抽检 + LLM 辅助判断</td><td>成本高，但能发现"编造"这类致命问题</td></tr>
    <tr><td><strong>业务层</strong></td><td>答案采纳率、追问率、转人工率、使用频次</td><td>埋点统计，需要真实用户量</td><td>最接近真实价值，但反馈周期最长</td></tr>
  </table>

分层的意义在于**排查顺序**：检索层不达标时，别急着优化生成——召回都没找到，生成层再好也只是在编。反过来，检索 Recall@10 已经 95% 但用户还不满意，问题就在生成层或者上下文组织上。

## 评测集怎么建

  <table>
    <tr><th>维度</th><th>建议</th><th>说明</th></tr>
    <tr><td>来源</td><td>真实提问优先</td><td>日志、群聊里的真实问法、badcase（第 07 篇）。自己编的问题会不自觉贴近文档用词，测不出真实难度</td></tr>
    <tr><td>规模</td><td>50 条可起步，200 条够用</td><td>追求 1000 条而拖延三个月，不如先有 50 条开始迭代</td></tr>
    <tr><td>类型覆盖</td><td>事实查询 / 比较 / 流程步骤 / 计算 / 应拒答</td><td><strong>别忘了"应拒答"</strong>——库里没有答案时能不能老实说不知道，这是最容易被忽略的一类</td></tr>
    <tr><td>标注内容</td><td>问题 + 期望命中的文档与章节 + 期望答案要点</td><td>「期望出处」是核心字段，它同时支撑检索层和生成层评测</td></tr>
    <tr><td>难度分层</td><td>简单 / 中等 / 困难各占一定比例</td><td>全是简单题会让指标虚高，掩盖真实问题</td></tr>
  </table>

其中**"应拒答"这一类值得单独强调**。企业知识库里绝大多数提问是库里没有答案的，如果系统对每个问题都能"编一个像模像样的回答"，那它的危险程度远高于"偶尔答不出来"。所以评测集里必须有一批"明知查不到"的问题，考核系统能不能守住底线。

## 自动评测能走多远

用模型当裁判（LLM-as-judge）确实能省大量人力，但它有几个已知的系统性偏差，需要主动对冲：

  <table>
    <tr><th>偏差</th><th>表现</th><th>对冲办法</th></tr>
    <tr><td>位置偏见</td><td>倾向选排在前面的答案</td><td>评测时随机打乱顺序，同一组评测跑两遍对比</td></tr>
    <tr><td>长度偏见</td><td>倾向认为更长、更详细的答案更好</td><td>把"简洁正确"和"冗长正确"都放进标准答案</td></tr>
    <tr><td>自我偏好</td><td>倾向给自己家模型生成的答案打高分</td><td>换一个不同来源的模型做裁判</td></tr>
    <tr><td>宽松倾向</td><td>打分整体偏高，区分度差</td><td>用"二选一"或"通过 / 不通过"替代 1-10 分</td></tr>
  </table>

务实的分工是：**检索层全自动（指标客观），生成层用 LLM 初筛 + 人工抽检 10%**。人工那 10% 要覆盖所有"应拒答"和"多文档综合"的题目，因为这些正是自动评测最容易漏判的地方。

## 上线：灰度，而且要分层灰度

上线策略上，有几条经验能少走弯路：

  <table>
    <tr><th>做法</th><th>理由</th></tr>
    <tr><td>先上"检索模式"，再上"生成模式"</td><td>就直接给出命中的原文片段 + 出处，让用户自己读。这一阶段能验证解析、切分、检索是否可用，且不会有幻觉风险</td></tr>
    <tr><td>先给 1 个部门用，别全员开放</td><td>选一个文档密集、反馈意愿强的部门（通常是技术或 HR），拿到真实 badcase 再推广</td></tr>
    <tr><td>界面上必须有反馈按钮</td><td>badcase 的采集入口。埋点日志只能看到行为，看不到"为什么不满"</td></tr>
    <tr><td>答案永远带出处</td><td>既是可信度来源，也是用户自查的路径——用户点开原文核实一次，胜过十次解释</td></tr>
    <tr><td>检索不到就明确说不知道</td><td>比编一个答案安全得多；也让"需要补什么文档"变成可统计的需求</td></tr>
  </table>

## 成本构成

知识库的持续成本由四块组成，量级差别很大：

  <table>
    <tr><th>环节</th><th>频次</th><th>成本驱动</th><th>优化方向</th></tr>
    <tr><td>入库 Embedding</td><td>一次性 + 增量</td><td>文档总量 × 模型单价</td><td>增量重建、批量调用、必要时本地部署（第 05 篇）</td></tr>
    <tr><td>向量检索</td><td>每次问答</td><td>索引规模与内存</td><td>量化、按需降维</td></tr>
    <tr><td>Rerank</td><td>每次问答</td><td>重排条数 × 模型单价</td><td>把重排条数从 30 降到 15，收益通常不明显下降</td></tr>
    <tr><td>生成</td><td>每次问答</td><td>输入输出 token 数</td><td>控制塞入的片段数与长度；简单问题用更小的模型</td></tr>
  </table>

有一件事值得提前算清楚：**每次问答塞进多少上下文，直接决定成本。** 塞 5 条和塞 15 条，token 差三倍，而质量往往只差一点点——用评测集验证"塞几条最优"，比拍脑袋省钱得多。

::: tip
判断一个知识库项目是否健康，看一个指标就够了：**有没有人每周在看 badcase 列表。** 有，它就在持续变好；没有，它只是"上线了"而已。
:::

到这里，一套能落地的企业知识库就完整了：解析、切分、元数据、检索、权限、维护、评测。最后一篇换个视角，看那些更"高级"的方案到底该在什么时候用——**进阶：GraphRAG / Agentic RAG 的适用边界**。
