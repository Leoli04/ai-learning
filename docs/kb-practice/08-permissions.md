# 权限与多租户：谁能看哪些文档

> 约 10 分钟 · 关键词：权限过滤、多租户、越权、审计

## 权限是最容易被低估的一环

做知识库 demo 时没人会想到权限——反正就 50 份公开文档。但企业环境里，同一个问题会撞上完全不同的答案：

  <table>
    <tr><th>文档</th><th>谁该看到</th><th>如果看错了会怎样</th></tr>
    <tr><td>薪酬结构与职级带宽</td><td>HR 与高管</td><td>内部矛盾、泄密</td></tr>
    <tr><td>客户合同与报价</td><td>对应销售与服务团队</td><td>商业机密外流，可能违约</td></tr>
    <tr><td>未披露的财报数据</td><td>财务与高管</td><td>合规风险，上市公司尤其严重</td></tr>
    <tr><td>系统架构与安全配置</td><td>技术团队</td><td>攻击面暴露</td></tr>
  </table>

这四个例子的共同点是：**它们都是"答对内容、但答错对象"**。检索没问题、生成也没问题，只是权限没做——而后果比答错更严重。所以权限不是"后续优化项"，**它是上线门槛**。

先把三个概念分清，很多讨论混乱都源于混用：

  <table>
    <tr><th>概念</th><th>回答的问题</th><th>知识库里的位置</th></tr>
    <tr><td>认证（Authentication）</td><td>你是谁</td><td>对接企业 SSO / OA 登录，通常不用自己实现</td></tr>
    <tr><td><strong>授权（Authorization）</strong></td><td>你能看哪些文档</td><td>知识库的核心工作量，本篇重点</td></tr>
    <tr><td>审计（Audit）</td><td>你看了什么</td><td>日志留存，合规检查与问题追责的依据</td></tr>
  </table>

## 可见范围有四种粒度

  <table>
    <tr><th>粒度</th><th>示例</th><th>特点</th></tr>
    <tr><td>角色级</td><td>全员 / 销售 / 人事 / 管理层</td><td>最粗，维护最省事，适合大多数制度类文档</td></tr>
    <tr><td>部门级</td><td>按组织架构树授权（含下级部门）</td><td>最常用；需要处理"跨部门协作"的例外</td></tr>
    <tr><td>用户级白名单</td><td>指定若干人可看</td><td>精细但难维护，容易漏加人导致"看不到"</td></tr>
    <tr><td>文档级继承</td><td>子文档继承父目录权限</td><td>省事，但改目录结构时会牵连一大片</td></tr>
  </table>

实践中通常是**角色 + 部门混合**：制度类走角色，业务文档走部门，敏感文档再加一层白名单。关键原则是——**权限尽量跟着组织架构走，而不是靠人工一个个指定人。** 组织架构变更时自动跟随，这是唯一能长期维护的方式。

选哪条路，取决于一个很具体的判断：**你们的权限多久变一次？** 如果一年调两次组织架构，元数据过滤完全够用；如果是多租户 SaaS，租户随时开通关闭，分区隔离更省心。

无论选哪种，有一条铁律不能破：**过滤必须发生在检索之前**（第 04 篇详细讲过）。顺序颠倒会同时损失召回和安全性——合法文档可能排在第 200 位进不了候选集，而越权内容已经在应用层被读出来了。

## 五个真实的越权漏洞

这几个坑几乎每个项目都会踩一两个：

  <table>
    <tr><th>漏洞</th><th>怎么发生的</th><th>怎么防</th></tr>
    <tr><td>只在前端隐藏</td><td>前端不显示文档列表，但检索接口照样返回内容</td><td>权限校验必须在<strong>检索层</strong>做，前端过滤只是体验优化</td></tr>
    <tr><td>缓存穿透</td><td>两个不同权限的用户问同一个问题，命中同一条缓存</td><td>缓存 key 必须包含用户身份或权限摘要，不能用问题文本做 key</td></tr>
    <tr><td>生成层泄漏</td><td>答案正确，但"你可能还想问"里带出了无权文档的标题</td><td>所有对外展示的内容（含推荐、引用列表）都走同一套权限校验</td></tr>
    <tr><td>权限变更延迟</td><td>员工调岗了，索引里的部门标签还是旧的</td><td>建立"组织架构变更 → 重刷标签"的触发链路，或用外部 ACL 实时判定</td></tr>
    <tr><td>聚合统计越权</td><td>用户只能看本部门文档，却问出了"全公司平均薪酬"</td><td>聚合类问题要判断<strong>统计口径是否越界</strong>，不能只看单篇文档权限</td></tr>
  </table>

最后一条特别值得说：**权限不只是"能不能看某篇文档"，还包括"能不能得到某个结论"。** 单个数据点都不敏感、聚合起来就敏感，这个场景在检索式系统里很容易被忽略——因为你的权限校验只管"这篇文档能不能读"，管不了"这些数字能不能加总"。

## 审计：不只是为了合规

检索日志要记这些字段：

  <table>
    <tr><th>字段</th><th>用途</th></tr>
    <tr><td>用户、时间、来源终端</td><td>合规审计、异常行为发现</td></tr>
    <tr><td>原始问题</td><td>badcase 分析（第 07 篇）——真实的用户问法是最宝贵的语料</td></tr>
    <tr><td>召回文档 ID 与排名分数</td><td>排查"为什么没搜到"，以及验证权限过滤是否生效</td></tr>
    <tr><td>最终答案与引用来源</td><td>出了问题能复现；也是评估生成质量的素材</td></tr>
  </table>

这里有个容易被忽略的收益：**审计日志和 badcase 库可以用同一份数据。** 一份带完整链路的日志，既能满足合规要求，又能直接拿来分析检索质量——一次采集两处受益，别做成两套。

::: tip
权限设计有一条实用的自检标准：**假设有恶意用户直接调用你的检索接口（绕过前端），他能拿到不该看的东西吗？** 如果答案是有可能，那这套权限就还没做完。
:::

到这一步，一个"能看、看得对、看得安全"的知识库已经成型了。但真实世界的文档不会停在原地——下一篇：**增量更新与版本管理：文档改了、删了怎么办**。
